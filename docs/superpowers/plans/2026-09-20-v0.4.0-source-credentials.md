# v0.4.0 来源凭据接线计划

**Goal:** 把 spec 已冻结的「可选凭据引用」从配置契约接到生产调用路径，解除
`community:github` 因匿名请求上限而永远无法取得 `ok` 的结构性阻塞，从而让 Task 5
六来源真实 smoke 门禁在 GitHub 一侧可达成。

**Tech Stack:** Python 3.12（stdlib）、`unittest`、Node 20+（`node --test`）、JSON Schema 2020-12。

**Spec:** [`v0.4.0 社区与学术来源设计`](../specs/2026-09-15-v0.4.0-community-academic-sources-design.md)
第「可选凭据引用」段；闸门定义见
[`社区证据与发布计划`](2026-09-15-v0.4.0-community-evidence-release.md) Task 5。

## 背景：为什么必须接线

spec 早已冻结凭据契约（用户配置 `acquisition.sourceCredentials["community:github"] =
{"ref":"env.GITHUB_TOKEN"}`；resolver 精确返回 `{"status":"absent"}` /
`{"status":"resolved","token":...}` / `{"status":"resolution-error"}`），适配器侧也已完整实现
并有单测覆盖。缺的是**生产调用路径上的接线**：`collect.py` 构造 `GitHubAdapter` 时从不传
`credential_resolver`，Registry 里也没有凭据引用字段，配置层无法声明 token。

后果是结构性的：匿名 `RequestBudget` 硬上限 total 24 / Search 9 / core 15 / GraphQL 0，而
默认三组查询 × 五类 entity 展开出的 lane 集合远超该上限，`community:github` 在现有配置下
**永远**输出 `partial/github-request-budget-exhausted`（`tests/acquisition/test_github_budget.py`
对该行为有显式断言）。Task 5 与来源级 cutover 因此被卡住。

## 结果

### 已验证

- 凭据接线生效：同一隔离运行时、同一 Registry，配置凭据后 `community:github` 的错误码由
  `github-request-budget-exhausted` 变为 `github-search-snapshot-changed`——说明请求已进入
  已认证预算（total 64 / Search 27 / core 31 / GraphQL 6），匿名上限不再是瓶颈。
- 未配置引用时匿名行为逐字不变（既有单测继续全绿）。
- 配置了引用但环境变量缺失时返回 `resolution-error`，不静默匿名。

### 未解决（不属本计划范围）

`community:github` 仍为 `partial`，根因是**首次运行的窗口无下界**：`Window` 的 `start`
来自上一次成功运行的 checkpoint，冷启动时为 `null`，于是 commit 搜索退化为全站自由文本
（实测 `agentic systems` 无日期限定符 `total_count` ≈ 4.02e6），必然翻页，而 spec 要求
「首页冻结 `total_count`，后页必须完全相等」，于是固定 `partial` 并重置回 page 1。
日期限定符本身有效（同查询加 `committer-date:>=` 近 24 小时为 5,354，近 1 小时为 380）。
是否收窄默认查询、或让 smoke 以稳态（有界窗口）运行，需要单独决策，见 Task 5 的阻塞清单。
