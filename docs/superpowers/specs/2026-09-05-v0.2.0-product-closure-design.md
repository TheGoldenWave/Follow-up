# Follow-up v0.2.0 产品闭环设计

状态：已批准实施

日期：2026-09-06

## 目的

`v0.2.0` 将 `v0.1.0` 之后已经完成的能力收束为一个可安装、可诊断、可审计的
中心化 Feed 产品版本。它正式发布 17 个官网 Blog 信源，让用户选择的频道真实影响
Digest 输入，提供经过验证的首次安装路径和面向用户的健康检查，并加入有界的个人
候选池、重要性选择以及基于投递状态的去重。Skill 的公开入口统一更名为 Follow-up。

本版本明确不包含本地采集、Python runtime、第三方 Adapter vendoring、认证 Sidecar、
长期反馈学习、分页个人 Feed、自动更新和自动回滚。这些能力从 `v0.3.0` 开始，按本地
采集计划继续建设。文档不得把规划能力描述成当前已实现能力。

## 用户入口

新安装将 Skill 注册名设置为 `follow-up`：

- 自然语言 onboarding：`set up follow-up`
- Slash command：`/follow-up`
- 可变用户数据继续保存在 `~/.follow-builders/`，保证已有数据兼容。
- 上游项目名 `follow-builders` 只保留在 attribution、provenance 和迁移记录中。

从 `v0.1.0` 升级时，必须明确告知用户注册名发生变化。得到确认后，安装器只替换旧
Skill registration，不重命名或删除用户数据目录。旧入口不再作为 `v0.2.0` 的公开
用户入口。

## 版本范围

### 官网 Blog 生产路径

版本包含 `config/feed-blogs.json` 中全部 17 个来源，并包含配置加载、
RSS/Atom/Sitemap/HTML/同源 JSON 发现、正文提取、采集编排、live validation、离线
fixture 和信源目录。单个来源或单条候选失败不得阻断其他 Blog 来源产出结果。

Blog 发现检查最近 72 小时，每个来源最多检查 12 个发现链接，每轮最多接收 3 篇有效
新文章。72 小时是采集失败后的恢复窗口，不是用户推送的时间窗。其他频道保留各自的
发现窗口。

### 频道选择

onboarding 中的来源偏好必须成为可执行配置。Digest preparation 读取顶层
`enabledChannels`，稳定值只能是 `x`、`podcasts`、`blogs`、`newsletters`、
`academic` 和 `zh-tech`。值必须唯一，未知值使配置无效，不能静默忽略。

为兼容 `v0.1.0`，旧配置缺少 `enabledChannels` 时运行时默认六类全开。新 onboarding
不得利用该兼容行为，必须显式写入用户选择；用户暂不启用任何频道时写入空数组 `[]`。
空数组合法，表示不读取中央 Feed，prepare 返回 `status: "no-channels"`、全零统计和
可操作提示，不运行摘要 Prompt，也不发送“无重要更新”。行业报告仍是规划项，不能
作为第七个 live channel 启用。

### 调度推送

用户只有在 onboarding 已完成，并分别批准 schedule 和精确 delivery destination 后，
才会收到自动消息。`v0.2.0` 支持 daily 与 weekly，不支持官网发布即刻提醒。
手动 `/follow-up` 不要求 schedule approval，但 Telegram 或 email 仍要求已有的精确目标
授权，或本次发送前即时确认。

一次成功完成 prepare 的计划任务有三种内容结果：

1. 存在达标候选：发送最多 10 条、按重要性排序的 Digest。
2. 所有启用来源均完整检查，但没有未推送候选达到门槛：daily 发送“今日无重要更新”，
   weekly 发送“本周无重要更新”。
3. 一个或多个启用来源未完整检查：有达标项时可发送并明确标记 `partial`；没有达标项
   时只能发送检查不完整状态，不能声称没有重要更新。

完整性按配置来源判断，而不是只按频道判断。每个来源在当前中央采集轮次必须提供
`ok`、`no-results`、`partial` 或 `error`：

| 状态 | 含义 |
|---|---|
| `ok` | 采集完成并产生至少一个有效候选，且没有已知候选损失。首选发现入口失败但声明的等价 fallback 完整成功时，可以只记录 warning。 |
| `no-results` | 采集无错误，但在来源窗口内没有符合条件的候选。 |
| `partial` | 至少恢复一个候选，但另一个合格候选提取失败、排序所需 enrichment 失败，或没有等价 fallback 能证明发现完整。 |
| `error` | 因发现、可达性、认证或 Schema 校验失败，没有产生可信结果。 |

频道 Feed 必须新鲜，且每个启用来源均为 `ok` 或 `no-results`，该频道才算完整。
`partial`、`error`、过期 Feed、缺失状态或无效 Feed 都会使用户运行不完整，并禁止使用
成功的 no-update 文案。partial 文案可以列出经过清理的来源名称，但不得泄露请求详情、
内部路径或 credential。

评分或 manifest 校验失败返回 `preparation-failed`，不能转换成 no-update。provider 明确
拒绝返回 `delivery-failed`。outbox 已进入 `pending` 后，若进程中断或 provider 结果无法
确定，则返回 `delivery-uncertain`。这些运行结果在本地和 `doctor` 中披露；系统不能在
目标渠道失败时假装已经发送成功。

## 滚动候选池

中心发布在保留六个 `v0.1.0` 分类 Feed 的同时，新增 `feed-candidates.json`。其 Schema
为 `contracts/candidate-feed.schema.json`，`schemaVersion` 为 `1.0`。分类 Feed 负责兼容
和当前快照，candidate Feed 负责 weekly、未推送筛选和后续个人 Feed 所需的连续历史。

envelope 包含 `generatedAt`、`initializedAt`、`continuousHistorySince`、retention 策略、
历史截断诊断、每个配置来源的一条当前状态，以及标准化 candidates。所有运行来源使用
显式且不可变的 namespaced source ID，例如 `x:karpathy`、`podcast:latent-space`、
`blog:anthropic-engineering`；运行时不得从 display name 推导身份。

每个 candidate 包含：

- `candidateId`：对 `candidate-v1`、channel、source ID，以及 source-native ID 计算
  SHA-256；没有 native ID 时使用 canonical URL。
- channel、source ID、可选 source-native ID、canonical URL、title、author、
  `publishedAt`、`firstSeenAt` 和 `lastSeenAt`。
- `contentFingerprint`：对 `content-v1` 与经过 Unicode 规范化、转小写、合并空白后的
  title 和 summarization content 计算 SHA-256。
- `summarizationContent`：一般来源最多 24,000 Unicode code points，Podcast transcript
  最多 80,000，并用 `contentTruncated` 说明是否截断。

所有 hash 输入都使用 UTF-8 bytes，每个字段编码为“十进制 byte length、一个冒号、字段
bytes”，再按协议顺序拼接。candidate ID、content fingerprint、request hash 和 event
cluster ID 均使用该 length-prefixed framing，避免边界碰撞。

URL canonicalization 删除 fragment、default port、无意义 trailing slash 差异和已知
tracking 参数，同时保留业务语义 query。每轮 generation 按 `candidateId` 将新结果与旧
artifact 合并：保留首次 `firstSeenAt`，采用当前内容和 `lastSeenAt`。跨来源相同
`contentFingerprint` 仍保留为独立候选，用于 corroboration；同一来源内重复 native ID
或 canonical URL 合并为一个候选。

首次 `v0.2.0` 上线只运行一次：

```text
node scripts/generate-feed.js --initialize-candidate-feed
```

初始化要求 candidate Feed 不存在，先验证当前六个分类 Feed，再标准化其保留内容，与
当前完整采集结果合并，并写入 `initializedAt`。普通 generation 遇到缺失或未初始化的
candidate artifact 必须失败；initialize 遇到已存在 artifact 也必须失败。这样既允许首次
迁移，又把后续意外历史丢失变成发布级错误。初始化将 `continuousHistorySince` 设置为
本次 collection start，不伪造分类快照之前的历史。仓库已提交的 candidate artifact 表示
初始化已经完成；workflow 的 initialize 输入只用于首次迁移或刻意删除 artifact 的隔离演练。

一般来源保留 15 个完整 UTC calendar days，Podcast 保留 30 个。collection start 所在
UTC 日是当前日，不算完整日，用户 timezone 不影响中央留存。按时间留存后，每个来源
至少保留最新 50 条，再按 publication time、first-seen time、candidate ID 应用全局
1,000 条上限。缺失或无效的旧 artifact 会使 generation 失败，不能静默发布不完整历史。

如果 per-source 或 global cap 删除了原本仍应保留的候选，artifact 必须记录
`historyTruncated: true`、受影响 source IDs、最老保留时间和 removed count，并保留按来源
计算的 first-seen 截断区间。请求区间越过连续或未截断历史时，prepare 返回
`incomplete-history`，禁止声称覆盖完整周期或发送成功 no-update 文案。

daily 和 weekly 都从用户尚未推送的 retained candidates 中排序。weekly 从上一次成功
周报后开始，最长覆盖 14 日；首次 weekly 只有在 `continuousHistorySince` 能证明已积累
最近 7 个完整日且无截断时才算 bootstrap 完成。在此之前只披露实际覆盖区间并返回
`incomplete-history`。更长的投递间隔或被 cap 截断的区间也按不完整历史处理。

## 重要性与组合选择

所有启用来源进入同一个候选集合。“来自所有来源”表示所有来源都有竞争资格，不要求
每个来源必选一条，也不允许 17 个官网 Blog 挤占其他频道。

selection stage 先把同一现实事件的候选聚为 event cluster，选择官方发布、原始论文、
作者原文或证据最强的一手来源作为 lead，其余独立来源作为 corroboration。每个事件使用
可审查的 100 分评分：

| 分项 | 权重 |
|---|---:|
| 对模型、产品、研究、API、安全或政策的潜在影响 | 30 |
| 与用户启用频道和明确 interests 的相关性 | 25 |
| 主来源权威性与证据质量 | 20 |
| 相对已推事件的新颖性 | 15 |
| 独立来源交叉印证 | 10 |

时效性属于资格和衰减规则，不能代替重要性。门槛为 60 分，目标为 6-10 条，但绝不为
凑数降低门槛；只有 1-5 条达标时就只发送这些内容。单个 source ID 最多占 2 个 lead
positions。当至少 3 个 channel 存在达标候选时，单一 channel 最多占 4 个 positions。
选择先从不同 source ID 各取排名最高项，再在组合上限内按排名补齐。并列顺序依次由
evidence、published time 和稳定 candidate ID 决定。

语义评分由当前 host Agent 使用 release-local `prompts/curate-digest.md` 完成；本版本
不调用独立托管的 ranking model。Agent 输出符合
`contracts/digest-selection.schema.json` v1.0 的 selection manifest。每个分项必须是
权重范围内整数，`totalScore` 必须严格等于分项之和。cluster 少于两个不同 source ID 时，
`corroboration` 必须为 0。

`eventClusterId` 是 `event-v1` 加该 cluster 全部 candidate IDs 的 SHA-256；candidate IDs
先按 UTF-8 byte order 排序，再使用相同 length-prefixed framing。每个 eligible candidate
必须且只能属于一个 cluster，包含低分项和受组合上限影响的未选项。manifest 记录 lead、
corroborating IDs、scores、简短 selection reason 和最终 `selectedEventClusterIds`。

validator 机械校验 Schema、ID、算术、门槛、cluster membership、delivery-ledger exclusion
和 portfolio limits。impact、relevance 与 clustering 的语义正确性由固定 evaluation fixture
和发布评审约束，不能伪装成纯机械证明。评分或验证失败时不得投递任何候选，也不得
fallback 为全量 Feed dump 或 no-update。

用户 interests 是可选本地配置。interests 和 selection manifests 均保存在
`~/.follow-builders/`，不进入公开 candidate Feed，并从诊断中脱敏。没有 interests 时，
relevance 只依据启用频道和 Follow-up 的通用 AI/技术范围，不臆造个人偏好。

## 投递状态机

`v0.2.0` 在 `~/.follow-builders/state/` 下引入 append-only delivery ledger 和 outbox。
它们与维护者的中央采集状态、未来 feedback 状态和 Knowledge 状态相互独立。

候选状态按事件推导：

- **unpushed**：存在于 rolling pool，且该用户没有成功投递记录。
- **delivery-uncertain**：属于 unresolved `pending` attempt；禁止自动重发，但不声称已送达。
- **pushed-unseen**：属于 `delivered` 或用户处置后的 `assumed-delivered` attempt；本版本不
  声称用户已阅读。

任何 stdout、Telegram 或 email handoff 前，系统必须先耐久写入 `pending` outbox。记录
包含随机 attempt ID、Digest ID、frequency、candidate IDs、event cluster IDs、destination
type 和 rendered message hash。provider 明确确认后追加 `delivered` 并保存非秘密 receipt；
明确拒绝后追加 `failed`，候选可在后续新 attempt 中重新获得资格。

若 handoff 后无法确认结果，attempt 保持 `pending`。为优先避免重复推送，普通自动选择
排除 pending candidates，不自动 retry 或 fallback。`doctor` 报告 unresolved attempt，用户
通过 `/follow-up resolve-delivery <attempt-id> <delivered|retry|suppress>` 处置：

- `delivered`：用户明确确认已收到，追加 `user-confirmed` receipt，不再次调用 provider。
- `retry`：先把旧 attempt 追加为 `superseded`，说明 duplicate risk 并取得新的外部目标
  确认，再创建同一 Digest 的 replacement pending。
- `suppress`：追加 `assumed-delivered`，保持候选排除，不声称 provider 成功。

只有 unresolved pending 接受这些转换，所有事件都 append-only 且有 timestamp。系统提供
的是 at-most-once automatic attempt，不声称跨外部 provider 的 transactional exactly-once。
每次 scheduled 或 manual selection 前都检查 ledger，因此普通第二次 `/follow-up` 不会自动
重发 pending、delivered 或 assumed-delivered candidates。delivery records 至少保留 90 日。

同一 canonical URL 即使内容变化，在本版本仍视为同一 candidate，不自动重发。可审计的
material-update identity 延后到后续 Feed contract。no-important-update attempt 的 candidate
IDs 为空，因此不改变任何条目状态。

## 个人 Feed 演进

`v0.2.0` 只交付有界 IM Digest，并实现 unpushed 与 pushed-unseen 的区别。后续个人 Feed
界面才引入显式 seen：用户在该界面打开条目、选择“标记已读”或提交条目级反馈时才改变
状态。发送消息和 IM read receipt 都不等于 seen。

后续界面可以按相同 ranking pool 分页加载更多内容，不改变上述投递语义。默认顺序为
unpushed 优先，其次 pushed-unseen；seen 通过历史或筛选访问。pagination cursor 由 score、
publication time 和 candidate ID 稳定组成，避免新采集轮次导致已遍历内容重复或跳过。

## 安装与信任模型

GitHub Release 是唯一正式分发源。安装器只接收已经通过独立 checksum、release manifest
和 archive critical-file 校验的归档。它检查 Node.js 兼容性，以 lockfile 安装依赖，将
release 发布为 immutable object，注册 `follow-up` Skill，保留用户数据，并运行 `doctor`。

release-local CLI：

```text
node scripts/install.js --platform <codex|claude-code|custom> [--skill-dir <absolute-path>] [--register] [--replace-follow-builders]
node scripts/doctor.js [--network] [--json]
```

`--register` 代表用户刚刚授权修改 Agent Skill 目录；没有该参数时只能验证并展示目标，
不能注册。内置目标为：

- Codex：`${CODEX_HOME:-$HOME/.codex}/skills/follow-up`
- Claude Code：`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/follow-up`
- Custom（包括本版本中的 Hermes 或 OpenClaw）：调用者必须提供绝对 `--skill-dir`，安装器
  不猜测路径。

安装器将 payload 发布到 `~/.follow-builders/releases/` 下带 owner token 的 immutable
object，并以 `~/.follow-builders/releases/0.2.0` 作为同目录相对 symlink pointer。三个
platform registration 都链接到该 pointer。Skill 运行命令优先使用宿主实际提供的 Skill
根目录；宿主没有提供时，统一从该已验证 pointer 执行，不依赖 Claude 专属环境变量。

installer 必须在任何写入或 npm lifecycle 前完成 archive-critical preflight；复制后再次
对 snapshot 做验证，依赖安装和 target-local doctor 成功后才发布 pointer。发布过程使用
锁、owner marker、completion marker、稳定 cwd、fsync 和原子 rename，避免竞争安装、路径
替换和半成品激活。已存在的 immutable release 只有在 marker、payload snapshot、manifest
和关键文件均重新验证通过时才可复用。

若同级存在旧 `follow-builders` registration，必须在解释入口更名后由用户显式传入
`--replace-follow-builders`。只有新 link 和本地 doctor 成功后才移除旧 link；失败时回滚
registration metadata，但保留已经完整发布、可复用的 immutable release。config、自定义
Prompt、credential、schedule、ledger、outbox 和其他 mutable 用户文件不得被重装覆盖。

release manifest 使用非循环完整性模型：checkout 模式对除 manifest 自身外的 tracked
Git tree 计算 `git-ls-tree-sha256-v1` digest，同时记录 58 个关键文件的 SHA-256；archive
模式在无 `.git` 环境中校验这 58 个文件。独立发布的 archive checksum 验证整个压缩包，
受保护 tag、不可变 GitHub Release、独立 manifest 和 checksum 才构成外部信任锚点。
validator 校验自身 hash 只是一层防篡改，不能单独建立信任。

`doctor` 检查 product version、manifest、Node runtime、dependencies、config、registration、
Feed contract、candidate history、unresolved pending，以及可选 network freshness/reachability。
本地完整性失败退出 `1`；无本地阻断但网络退化退出 `2`；健康或仅 warning 退出 `0`；CLI
用法错误退出 `64`。网络检查中 48 小时内为 healthy，超过 48 小时至 7 日为 stale warning，
超过 7 日或不可达为 degraded。JSON 输出只包含经过脱敏的 severity、scope、blocking 和
有限 evidence。

本版本不声明自动发现更新、自动 staging、自动 activation 或 executable rollback。

## 兼容与安全

- 旧配置缺少 `enabledChannels` 时继续消费全部六类 live Feed；新 onboarding 必须显式写入。
- 没有 delivery ledger 的旧用户从空 ledger 开始，不能把中央采集状态当作用户已收到或
  已阅读的证据。
- 安装不得覆盖 `~/.follow-builders/` 中任何已有 mutable 文件，除非当前动作已经单独授权。
- Skill registration、credential 写入、schedule mutation 和 external send 是四类独立副作用，
  必须分别取得紧邻操作的授权。
- release archive 只能包含 tracked files，并继续经过 checksum、manifest、provenance、
  secret scan、dependency license、clean install 和 reinstall preservation 门禁。
- 所有输出路径、ledger、outbox、journal 和 registration path 都拒绝越界、危险 symlink、
  非普通文件和并发身份替换。
- 诊断不得回显 secret、credential、内部绝对路径或不受限 provider receipt。

## 验收标准

- `VERSION`、package metadata、changelog、release manifest 和 archive 都标识 `0.2.0`；tag
  与 GitHub Release 只有在 reviewed commit 通过 required checks 后由外部发布流程创建。
- 17 个官网 Blog 均有有效 production config 和离线 fixture，14 个 Node-live 来源通过；
  三个已记录路由例外保留准确的 Browser-live provenance。单源失败不阻断其他来源。
- disabled channel 不贡献 item 或 Prompt input；旧配置仍启用六类，新 onboarding 的子集
  不扩展，`[]` 不读取 candidate Feed 并返回 `no-channels`。
- candidate Feed 只能初始化一次，之后持续增量合并并执行有界留存；截断和完整性披露准确。
- daily/weekly 只选择 unpushed candidates；pending、delivered、assumed-delivered 不普通重发。
