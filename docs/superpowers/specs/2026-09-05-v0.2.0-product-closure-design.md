# Follow-up v0.2.0 Product Closure Design

Status: Approved

Date: 2026-09-05

## Purpose

`v0.2.0` turns the work completed after `v0.1.0` into a coherent, installable
centralized-Feed product release. It publishes the 17-source official Blog
collector, makes configured channel choices affect Digest input, provides a
verified first-install path and a user-facing health check, and renames the Skill
entry point to Follow-up.

Local acquisition, Python runtime work, third-party Adapter vendoring, authenticated
Sidecars, and automatic rollback are explicitly outside this release. They begin in
`v0.3.0` under the local-acquisition plan.

## User Entry Point

New `v0.2.0` installations register the Skill as `follow-up`.

- Natural-language onboarding: `set up follow-up`
- Slash command: `/follow-up`
- Existing mutable user data remains under `~/.follow-builders/` for compatibility.
- The upstream project name `follow-builders` remains unchanged in attribution and
  provenance records.

An upgrade from `v0.1.0` must explain that the registered Skill name changes. After
confirmation, installation removes or replaces only the old Skill registration; it
must not rename or delete the existing user-data directory.

## Release Scope

### Official Blog production path

The release includes all 17 sources in `config/feed-blogs.json`, the configuration
loader, RSS/Atom/Sitemap/HTML/same-origin JSON discovery, extraction, collection,
live validation, fixtures, and source-catalog documentation. One source failure must
not prevent unrelated Blog sources from producing results.

### Channel selection

The existing onboarding preference becomes executable behavior. Digest preparation
loads the top-level `enabledChannels` array. Its stable values are `x`, `podcasts`,
`blogs`, `newsletters`, `academic`, and `zh-tech`. Missing `enabledChannels` defaults
to all six values for `v0.1.0` compatibility. Values must be unique and unknown values
make the configuration invalid rather than being silently ignored.

An empty array is valid and means that no central Feed is fetched. Digest preparation
returns `status: "no-channels"`, zero content statistics, and an actionable message
instead of invoking summary prompts over empty input. Industry reports remain planned
and cannot be enabled as a live Feed in this release.

### Installation and diagnostics

GitHub Releases remain the canonical distribution source. A verified installer runs
only after the archive and manifest have passed the release trust checks. It checks
Node.js compatibility, installs locked JavaScript dependencies, registers the
`follow-up` Skill for the selected supported Agent, preserves existing user data,
and runs `doctor`.

The release-local interface is:

```text
node scripts/install.js --platform <codex|claude-code|custom> [--skill-dir <absolute-path>] [--register] [--replace-follow-builders]
node scripts/doctor.js [--network] [--json]
```

`--register` represents the immediately preceding user approval to modify the Agent's
Skill directory; without it installation validates and reports the proposed path but
does not register anything. The built-in registration targets are:

- Codex: `${CODEX_HOME:-$HOME/.codex}/skills/follow-up`
- Claude Code: `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/follow-up`
- Custom, including Hermes or OpenClaw in `v0.2.0`: the caller must provide an
  absolute `--skill-dir`; the installer never guesses it.

The installer copies the verified release to
`~/.follow-builders/releases/0.2.0/` and registers the Skill with a link to that
immutable release directory. If a sibling `follow-builders` registration exists,
replacement requires the separate `--replace-follow-builders` flag after the user is
told about the command rename. The old registration is removed only after the new
link and local checks succeed.

`doctor` reports product version, manifest consistency, runtime compatibility,
configuration validity, Skill registration, Feed contract compatibility, and
per-channel freshness/reachability. Network failures remain channel- or source-level
findings rather than a false global installation failure.

Offline checks are blocking. A version or manifest mismatch, unsupported Node.js,
invalid local configuration, incomplete dependency installation, or missing requested
Skill registration exits `1`. Optional `--network` checks classify a Feed generated
within 48 hours as healthy, over 48 hours through 7 days as a non-blocking stale
warning, and more than 7 days as degraded. Unreachable or invalid remote Feeds are
also degraded. Healthy and warning-only results exit `0`; any degraded network result
exits `2`, which the installer reports but does not treat as a failed local
installation. Invalid CLI usage exits `64`. JSON output carries severity, scope,
blocking status, and redacted evidence.

Automatic update discovery, staging, atomic activation, and executable rollback are
not claimed by `v0.2.0`.

## Compatibility and Safety

- Old configuration without channel-selection fields continues to consume all six
  live Feeds.
- Installation never overwrites custom prompts, delivery credentials, schedules, or
  other files under `~/.follow-builders/` without separate authorization.
- Registering a Skill, writing credentials, and creating a schedule remain separate
  user-approved actions.
- Release archives contain tracked files only and retain the existing checksum,
  manifest, provenance, secret-scan, and clean-install gates.

## Acceptance Criteria

- `VERSION`, package metadata, changelog, release manifest, archive, tag, and GitHub
  Release all identify `0.2.0`.
- All 17 official Blog sources have valid production configuration and offline
  fixtures; their documented live-validation evidence remains accurate.
- A disabled channel contributes no items or prompt input; legacy configuration
  still receives all six live channels.
- A verified clean installation registers `follow-up`, accepts `set up follow-up`
  and `/follow-up`, installs locked dependencies, and passes `doctor`.
- Reinstallation and upgrade preserve every pre-existing mutable user file under
  `~/.follow-builders/` byte-for-byte except for changes separately authorized during
  onboarding. Installer-owned release directories and activation metadata may be
  added or replaced as defined by the installation contract.
- Documentation does not claim local acquisition, Sidecars, persistent feedback,
  industry-report Feed support, or automatic rollback is implemented.
