# Follow-up v0.2.0 Product Closure Design

Status: Draft revision pending user review

Date: 2026-09-05

## Purpose

`v0.2.0` turns the work completed after `v0.1.0` into a coherent, installable
centralized-Feed product release. It publishes the 17-source official Blog
collector, makes configured channel choices affect Digest input, provides a
verified first-install path and a user-facing health check, adds a bounded personal
Digest queue with delivery-state deduplication, and renames the Skill entry point to
Follow-up.

Local acquisition, Python runtime work, third-party Adapter vendoring, authenticated
Sidecars, and automatic rollback are explicitly outside this release. They begin in
`v0.3.0` under the local-acquisition plan.

## User Entry Point

New `v0.2.0` installations register the Skill as `follow-up`.

- Natural-language onboarding: `set up follow-up`
- Slash command: `/follow-up`
- Existing mutable user data remains under `~/.follow-builders/` for compatibility.
- The upstream project name `follow-builders` remains unchanged in attribution and
  provenance records.

An upgrade from `v0.1.0` must explain that the registered Skill name changes. After
confirmation, installation removes or replaces only the old Skill registration; it
must not rename or delete the existing user-data directory.

## Release Scope

### Official Blog production path

The release includes all 17 sources in `config/feed-blogs.json`, the configuration
loader, RSS/Atom/Sitemap/HTML/same-origin JSON discovery, extraction, collection,
live validation, fixtures, and source-catalog documentation. One source failure must
not prevent unrelated Blog sources from producing results.

### Channel selection

The existing onboarding preference becomes executable behavior. Digest preparation
loads the top-level `enabledChannels` array. Its stable values are `x`, `podcasts`,
`blogs`, `newsletters`, `academic`, and `zh-tech`. Missing `enabledChannels` defaults
to all six values for `v0.1.0` compatibility. Values must be unique and unknown values
make the configuration invalid rather than being silently ignored.

An empty array is valid and means that no central Feed is fetched. Digest preparation
returns `status: "no-channels"`, zero content statistics, and an actionable message
instead of invoking summary prompts over empty input. Industry reports remain planned
and cannot be enabled as a live Feed in this release.

### Scheduled delivery

A user receives an automatic message only after onboarding is complete and the user
has separately approved both a schedule and its delivery destination. `v0.2.0`
supports daily and weekly schedules; it does not provide immediate alerts when an
official site publishes an article. `/follow-up` is the unified manual entry point:
it starts onboarding when configuration is incomplete and requests an on-demand
Digest when onboarding is complete.

Every successfully prepared scheduled run produces one of three content outcomes:

1. Qualifying candidates exist: deliver a ranked Digest containing up to 10 items.
2. All enabled channels were checked successfully but no unpushed candidate meets the
   importance threshold: deliver a schedule-aware localized status such as "No
   important updates today" for daily delivery or "No important updates this week"
   for weekly delivery.
3. One or more enabled channels could not be checked: deliver available qualifying
   items when present and clearly label the run partial; when no items qualify, send
   an incomplete-check status instead of claiming that nothing important happened.

An empty `enabledChannels` array does not generate a daily no-update message. It is a
configuration state surfaced by onboarding and `doctor`.

Completeness is evaluated per configured source, not merely per channel. Each enabled
source reports `ok`, `no-results`, `partial`, or `error` for the current central
collection run. A channel is complete only when its Feed is fresh and every enabled
source is `ok` or `no-results`. Any `partial`, `error`, stale Feed, missing status, or
invalid Feed makes the user run partial and suppresses the successful no-update
wording. Source failures are named in the partial status without leaking request or
credential details.

Source statuses have fixed meanings:

| Status | Meaning |
|---|---|
| `ok` | Collection completed and produced one or more valid candidates without known candidate loss. A failed preferred discovery path may remain a warning only when a declared equivalent fallback completes successfully. |
| `no-results` | Collection completed without errors and found no eligible candidate inside the source window. |
| `partial` | At least one candidate was recovered, but another eligible discovered item failed extraction, an enrichment required for ranking failed, or no equivalent fallback could prove discovery completeness. |
| `error` | The source produced no trustworthy result because discovery, reachability, authentication, or schema validation failed. |

Digest scoring or manifest-validation failure produces `preparation-failed`; it never
produces a no-update message. A known destination rejection produces
`delivery-failed`. A process interruption or indeterminate provider result after the
outbox enters `pending` produces `delivery-uncertain`. These operational outcomes are
reported locally and by `doctor`; Follow-up does not pretend it successfully sent a
status through a destination that failed.

### Rolling candidate pool

The collection lookback controls discovery recovery, not what a user has already
received. Official Blog discovery continues to inspect the most recent 72 hours and
up to 12 candidate links per source, extracting at most three valid new posts per
source per collection run. The other source-specific discovery windows remain
independent.

To make weekly delivery and later retrieval reliable, central Feed publication adds a
`feed-candidates.json` rolling artifact while retaining the six existing category
Feeds for `v0.1.0` compatibility. Its JSON Schema is
`contracts/candidate-feed.schema.json` with schema version `1.0`.

The envelope contains `generatedAt`, `continuousHistorySince`, retention policy,
history-truncation diagnostics, one current status record for every configured
source, and normalized candidates. V0.2 adds explicit immutable source IDs to source
configuration using namespaced forms such as
`x:karpathy`, `podcast:latent-space`, and `blog:anthropic-engineering`; runtime code
never derives identity from display names.

Each candidate contains:

- `candidateId`: SHA-256 of `candidate-v1`, channel, source ID, and the source-native
  ID, falling back to canonical URL when no native ID exists;
- channel, source ID, source-native ID when present, canonical URL, title, author,
  publication time, `firstSeenAt`, and `lastSeenAt`;
- `contentFingerprint`: SHA-256 of `content-v1` plus Unicode-normalized, lower-cased,
  whitespace-collapsed title and summarization content;
- summarization content capped at 24,000 UTF-8 characters, or 80,000 for podcast
  transcripts, together with a `contentTruncated` flag.

Hash inputs use UTF-8 bytes with each field serialized as its decimal byte length,
one colon, then the field bytes; fields are concatenated in the documented order.
This length-prefixed framing applies to candidate IDs, content fingerprints, and event
cluster IDs.

URL canonicalization removes fragments, default ports, trailing-slash differences,
and known tracking parameters while preserving semantic query parameters. On every
generation, new category results are merged into the prior valid rolling artifact by
`candidateId`; `firstSeenAt` is preserved and current content plus `lastSeenAt` wins.
Exact cross-source content fingerprints are retained as separate candidates so they
can provide corroboration, but duplicate native identities or canonical URLs within a
source collapse to one candidate.

The first `v0.2.0` deployment runs
`node scripts/generate-feed.js --initialize-candidate-feed` exactly once. Initialization
requires that no rolling artifact exists, validates all six current category Feeds,
normalizes their retained contents, merges the current collection results, and writes
an `initializedAt` marker. Normal generation refuses a missing or uninitialized prior
artifact, and initialization refuses to overwrite one. This makes later accidental
history loss a fatal publication error without making first deployment impossible.
Initialization sets `continuousHistorySince` to its own collection start; it does not
pretend that the current category snapshots contain earlier history.

Daily sources are retained for 15 complete days and podcasts for 30 days. After
retention pruning, the newest 50 candidates per source remain eligible, followed by a
global cap of 1,000 candidates using publication time, then first-seen time, then
candidate ID. A missing or invalid prior rolling artifact fails that generation rather
than silently publishing an incomplete weekly history.

If a per-source or global cap removes any otherwise retained candidate, publication
records `historyTruncated: true`, the affected source IDs, oldest retained timestamp,
and removed count. Digest preparation treats requested time outside continuous,
untruncated history as `incomplete-history`. That state suppresses successful
no-update wording and prevents the Digest from claiming complete period coverage.

Daily and weekly Digests both rank the user's unpushed portion of this pool. A weekly
Digest covers candidates accumulated since the prior successful weekly delivery, up
to a maximum 14-day coverage window; the first weekly Digest uses the most recent
seven complete days only after `continuousHistorySince` proves they have accumulated
without truncation. Before then it reports bootstrap history as incomplete and labels
the actual covered interval. A longer delivery gap or cap-truncated interval is also
reported as incomplete history rather than silently described as full coverage.

### Importance and portfolio selection

All enabled sources compete in one candidate set. "Across all sources" means every
source is eligible; it does not require one item from every source or allow 17 official
Blogs to crowd out the other channels.

The selection stage groups candidates that describe the same event, chooses the
official or otherwise strongest primary source as the lead item, and retains secondary
links as corroboration. Each event receives a reviewable 100-point score:

| Component | Weight |
|---|---:|
| Potential impact on models, products, research, APIs, security, or policy | 30 |
| Relevance to the user's enabled channels and stated interests | 25 |
| Primary-source authority and evidence quality | 20 |
| Novelty relative to previously pushed events | 15 |
| Independent corroboration | 10 |

Recency is an eligibility and decay rule rather than a substitute for importance.
Selection targets 6-10 items, but never pads a Digest with low-value content: it may
send 1-5 items when only that many pass the threshold. It selects no more than two
lead items from one source. When at least three channels have qualifying candidates,
no channel may occupy more than four positions. Selection first takes the highest
ranked item from distinct sources, then fills remaining positions by score within
those portfolio limits. Ties are resolved deterministically by evidence quality,
publication time, and stable candidate ID.

The host Agent performs semantic scoring using the release-local
`prompts/curate-digest.md`; `v0.2.0` does not call a separately hosted ranking model.
It emits a selection manifest conforming to
`contracts/digest-selection.schema.json` version `1.0`. Every score component is an
integer from zero through its stated weight and `totalScore` must equal their sum. A
candidate qualifies at 60 points. Corroboration can score above zero only when the
cluster contains candidates from at least two source IDs.

Each event cluster ID is the SHA-256 of `event-v1` plus its byte-order sorted candidate
IDs using the same length-prefixed framing. A
candidate may belong to only one cluster. The manifest records one lead candidate,
zero or more corroborating candidate IDs, component scores, and a concise selection
reason. The deterministic validator checks IDs, arithmetic, threshold, cluster
membership, delivery-ledger exclusion, and portfolio limits. Semantic correctness of
impact, relevance, and clustering is covered by fixed evaluation fixtures and release
review rather than falsely claimed as mechanically provable. If scoring or validation
fails, no candidates are delivered and the run reports Digest generation failure; it
must not fall back to dumping every Feed item or to the no-update message.

User interests are optional local configuration. They and all selection manifests
remain under `~/.follow-builders/`, never enter the public rolling Feed, and are
redacted from diagnostics. When no interests are configured, relevance is based only
on enabled channels and the general Follow-up product scope.

### Personal delivery state

`v0.2.0` introduces a local append-only delivery ledger and outbox under
`~/.follow-builders/state/`. They are separate from the maintainer's central
collection state and from future feedback or Knowledge state.

Candidate state is derived as follows:

- **Unpushed:** present in the rolling candidate pool with no successful delivery
  record for this user.
- **Delivery uncertain:** included in an unresolved `pending` attempt. It is excluded
  from automatic resend but is not claimed as delivered.
- **Pushed, unseen:** included in a `delivered` or user-resolved `assumed-delivered`
  attempt. `v0.2.0` does not claim the user has read it.

Before any stdout, Telegram, or email handoff, Follow-up atomically writes a `pending`
outbox record containing a random attempt ID, Digest ID, selected candidate IDs, event
clusters, destination type, and a hash of the rendered message. A confirmed provider
response changes it to `delivered` and stores the non-secret provider receipt. A known
failure changes it to `failed`, making its candidates eligible for a later attempt.

If the process stops after handoff but before confirmation, the attempt remains
`pending`. Pending candidates are excluded from automatic selection to favor no
duplicate pushes over automatic retry; `doctor` reports the uncertain attempt and the
user resolves it through `/follow-up resolve-delivery <attempt-id>
<delivered|retry|suppress>` or the equivalent natural-language action:

- `delivered` records the provider result as user-confirmed delivery.
- `retry` first records the old attempt as `superseded`, explains the duplicate risk,
  obtains fresh confirmation for the external destination, and creates a new pending
  attempt for the same Digest.
- `suppress` records `assumed-delivered` and keeps the candidates excluded without
  sending again.

Only an existing unresolved pending attempt accepts these transitions, and every
resolution is append-only and timestamped. This is an at-most-once automatic attempt
policy, not a claim of transactional exactly-once delivery across external providers.
The ledger is checked before every scheduled or manual selection, so a normal second
`/follow-up` run cannot automatically resend delivered, assumed-delivered, or pending
candidates. Delivery records are retained for at least 90 days.

`v0.2.0` treats the same canonical URL as the same candidate even when content changes
and does not automatically resend it. Material-update versioning is deferred until a
later Feed contract defines auditable update identity and significance.

The no-important-update message records the run outcome but contains no candidate IDs
and therefore does not change item state.

### Personal Feed evolution

`v0.2.0` delivers only the bounded IM Digest and implements unpushed versus pushed,
unseen state. A later personal Feed surface adds the explicit interaction that changes
an item to **seen**: opening it through that surface, choosing "mark read", or giving
item-specific feedback. Sending a message and IM read receipts never count as seen.

That later surface may page through the same ranked pool and request more items without
changing the delivery semantics above. Its default order is unpushed first, then pushed
but unseen, with seen items available through history or explicit filters. Pagination
uses a stable cursor over score, publication time, and candidate ID so new collection
runs do not duplicate or skip items already traversed by the user.

### Installation and diagnostics

GitHub Releases remain the canonical distribution source. A verified installer runs
only after the archive and manifest have passed the release trust checks. It checks
Node.js compatibility, installs locked JavaScript dependencies, registers the
`follow-up` Skill for the selected supported Agent, preserves existing user data,
and runs `doctor`.

The release-local interface is:

```text
node scripts/install.js --platform <codex|claude-code|custom> [--skill-dir <absolute-path>] [--register] [--replace-follow-builders]
node scripts/doctor.js [--network] [--json]
```

`--register` represents the immediately preceding user approval to modify the Agent's
Skill directory; without it installation validates and reports the proposed path but
does not register anything. The built-in registration targets are:

- Codex: `${CODEX_HOME:-$HOME/.codex}/skills/follow-up`
- Claude Code: `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/follow-up`
- Custom, including Hermes or OpenClaw in `v0.2.0`: the caller must provide an
  absolute `--skill-dir`; the installer never guesses it.

The installer copies the verified release to
`~/.follow-builders/releases/0.2.0/` and registers the Skill with a link to that
immutable release directory. If a sibling `follow-builders` registration exists,
replacement requires the separate `--replace-follow-builders` flag after the user is
told about the command rename. The old registration is removed only after the new
link and local checks succeed.

`doctor` reports product version, manifest consistency, runtime compatibility,
configuration validity, Skill registration, Feed contract compatibility, and
per-channel freshness/reachability. Network failures remain channel- or source-level
findings rather than a false global installation failure.

Offline checks are blocking. A version or manifest mismatch, unsupported Node.js,
invalid local configuration, incomplete dependency installation, or missing requested
Skill registration exits `1`. Optional `--network` checks classify a Feed generated
within 48 hours as healthy, over 48 hours through 7 days as a non-blocking stale
warning, and more than 7 days as degraded. Unreachable or invalid remote Feeds are
also degraded. Healthy and warning-only results exit `0`; any degraded network result
exits `2`, which the installer reports but does not treat as a failed local
installation. Invalid CLI usage exits `64`. JSON output carries severity, scope,
blocking status, and redacted evidence.

Automatic update discovery, staging, atomic activation, and executable rollback are
not claimed by `v0.2.0`.

## Compatibility and Safety

- Old configuration without channel-selection fields continues to consume all six
  live Feeds.
- Existing users without a delivery ledger start with an empty local ledger; the
  migration never interprets central collection state as proof that a user received
  or saw an item.
- Installation never overwrites custom prompts, delivery credentials, schedules, or
  other files under `~/.follow-builders/` without separate authorization.
- Registering a Skill, writing credentials, and creating a schedule remain separate
  user-approved actions.
- Release archives contain tracked files only and retain the existing checksum,
  manifest, provenance, secret-scan, and clean-install gates.

## Acceptance Criteria

- `VERSION`, package metadata, changelog, release manifest, archive, tag, and GitHub
  Release all identify `0.2.0`.
- All 17 official Blog sources have valid production configuration and offline
  fixtures; their documented live-validation evidence remains accurate.
- A disabled channel contributes no items or prompt input; legacy configuration
  still receives all six live channels.
- Daily and weekly runs select only unpushed candidates from a bounded rolling pool;
  a normal second run excludes candidates in pending, delivered, or
  assumed-delivered attempts.
- A successful scheduled check with zero qualifying candidates sends the localized
  no-important-update status; a partial source check never uses that success wording.
- Selection targets 6-10 important items without padding, collapses duplicate events,
  enforces source/channel portfolio limits, and carries a validated selection trace.
- Sending an item marks it pushed but unseen. The explicit interaction that marks it
  seen is intentionally deferred to the later personal Feed surface.
- A verified clean installation registers `follow-up`, accepts `set up follow-up`
  and `/follow-up`, installs locked dependencies, and passes `doctor`.
- Reinstallation and upgrade preserve every pre-existing mutable user file under
  `~/.follow-builders/` byte-for-byte except for changes separately authorized during
  onboarding. Installer-owned release directories and activation metadata may be
  added or replaced as defined by the installation contract.
- Documentation does not claim local acquisition, Sidecars, general persistent
  feedback learning, industry-report Feed support, paginated personal Feed UI, or
  automatic rollback is implemented.
